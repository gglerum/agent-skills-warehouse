# Decision map

Agree what reaching the destination means. Read existing decisions first. Use a map only when real uncertainty spans sessions; a clear single task needs no extra structure.

Keep MAP.md as an index. Each ticket carries a question, type (research, prototype, human discussion or task), prerequisites, owner/claim and state. Create real ticket files before wiring their dependencies. The frontier contains open unclaimed tickets whose prerequisites are resolved. Keep unknown territory separate from ruled-out scope.

Resolve one authorized frontier ticket, record the answer and evidence in that ticket, update the map with a short link, and propagate only decisions that belong in an existing authoritative record. Distinguish planning from executing the resulting design. Use a handoff to identify the next frontier; never answer for a human participant.
